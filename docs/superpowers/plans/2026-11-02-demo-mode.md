# Demo mode implementation plan

> For agentic workers: use superpowers:executing-plans. Steps use checkboxes.
> The engineer asked for the work to be built in this session ("start it and
> finish it"), so tasks name files, interfaces and tests; the code is written
> test first while executing each task.

**Goal:** a public demo of Latte inside production, isolated in a `demo`
Postgres schema, behind `DEMO_MODE`.

**Architecture:** a second pool with `search_path = demo, extensions` and a
second copy of the API router built on demo dependencies (demo pool, storage
prefixed `demo/`, enqueue tagged `workspace: "demo"`). Demo visitors carry an
`ldemo_` token; an allowlist guards what they may do.

**Tech stack:** Node 24, TypeScript, Express 5, Zod 4, pg, jose, vitest;
React 19, TanStack Query and Router, coss ui.

**Spec:** `docs/superpowers/specs/2026-11-02-demo-mode-design.md`

## Global constraints

- `public` is never on the demo search path.
- No raw IP, user agent or browser signal is stored or logged; only
  `HMAC-SHA256(key("fingerprint"), ...)`.
- `DEMO_MODE` defaults to false; on requires `DEMO_SECRET` (32+ chars).
- `DEMO_DAILY_UPLOADS` defaults to 50; one transcript, 200 lines, 20,000
  characters per demo upload.
- No new dependency. No migration file edited; new files only.
- Commit subjects match the CI regex; ids `[SCC-11-1-n]`.

## Review focus

1. The main purge's orphan sweep walks every bucket folder: it must skip
   `demo/`, or it deletes demo audio (test in task 6).
2. A pooled demo connection must keep its search path after an error or a
   `RESET`-like statement (test: a failed query, then `current_schemas`).
3. Two parallel demo uploads from one device: exactly one call (task 4).
4. An `ldemo_` token while `DEMO_MODE=false` must be 401, not fall through
   to the Supabase verifier with a confusing error (task 2).
5. A demo visitor's review write on a seeded call, or on another visitor's
   call, is 403 (task 3).

## Tasks

### Task 1: Config, pool search path, demo schema migration

- [ ] Test (`config.test.ts`): `DEMO_MODE=true` without `DEMO_SECRET` fails;
  defaults are false and 50.
- [ ] Test (integration `demo-schema.test.ts`): after `migrate` and
  `migrateDemo`, every `public` base table exists in `demo` with the same
  column names; a demo pool connection reports `current_schemas(false)` as
  `{demo,extensions}` (or `{demo}` where `extensions` does not exist), also
  after a failed query; a demo-pool query on a table only in `public` fails.
- [ ] Implement `createPool({ searchPath })` with `options: -c search_path=...`
  plus `SET search_path` on connect; `migrateDemo(pool)` creates the schema,
  runs `migrate` on a demo-path pool, then `migrations/demo/*.sql` recorded
  as `demo/<file>`; `make migrate` runs both.
- [ ] Commit `feat(api): build an isolated demo schema behind DEMO_MODE [SCC-11-1-2]`.

### Task 2: Demo identity, token and session endpoints

- Produces: `demoKeys(secret)`, `fingerprintOf(keys, ip, signals)`,
  `signDemoToken(keys, visitorId, now)`, `verifyDemoToken(keys, token)`;
  `DEMO_TOKEN_PREFIX = "ldemo_"`.
- [ ] Unit tests for keys: labels give different keys; token round trip;
  wrong secret, expired, wrong audience, missing prefix all rejected.
- [ ] Integration tests: `GET /api/demo` answers `{enabled:false}` without
  demo deps; `POST /api/demo/sessions` is 404 when off; when on it creates a
  visitor and a manager profile in `demo` only, stores a 64-hex hash and no
  IP or user agent anywhere; the sixth session in an hour from one IP is 429;
  the token reads `/api/me` as "Demo visitor"; an expired visitor is 401; an
  `ldemo_` token with demo off is 401.
- [ ] Commit `feat(api): sign visitors in to the demo with a throwaway identity [SCC-11-1-3]`.

### Task 3: Demo router and allowlist

- [ ] Implement `apiRoutes`, the demo branch, `demoGuard`, scope
